# 主动评估方法

## 目标、差距与授权

参考阿里技术《Personal Agent 落地思考：主动性从哪来，又卡在哪？》：主动性来自“目标 − 现状”的差距。对本任务而言，目标是用户明确给出的交易与基本面方法论，不是模型猜测的兴趣。

- 目标清晰且可检查，才能由 Agent 找差距；目标本身变化时先对齐，不沿旧目标盲跑。
- 目标授权不覆盖全部子任务。读取证据与发送提醒可以自动，修改规则、写正式研究、真实交易仍需各自授权。
- 是否能自动执行看失败代价：能否撤回、影响谁、能否验证。高代价动作留在建议或审批，不因系统能调用就直接执行。

## 候选类型与证据

- `trend_state`：读取对应 R-XXX 和趋势/仓位框架。检查参考交易日、状态迁移、计数器、条件组和数据缺口；趋势读数不替代集中度轴、领导股或盘中承接证据。
- `catalyst`：读取正式事件和 `source_refs` 的 Raw 来源。检查硬字段、基准增量、反向链条、来源权重和不确定性；S/A 是入账门槛，不是必须推送的门槛。
- `framework_review`：读取框架复核规则。提醒体检不等于宣告产业转向，旧 stance 不能冒充当前事实。
- `framework_change`：检查变化是否改变目标、触发器或证据口径。纯排版变化不需要提醒；目标语义变化需持续对齐。
- `scheduled_review`：是重新检查目标与数据的机会，不是必须生成日报或消息。没有新差距就静默。

## 何时提醒

提醒需要同时成立：证据足够、相对上次有增量、与目标直接相关、时效内需要用户复核。不能只因“有新闻”“分数变化”“一个阈值触发”就打扰。

- 防守类信号要看完整条件组，宏观单项不能替代交易规则。
- 拐点要区分事实变化与模型推断，供需、价格、产能、库存、交期最好相互验证。
- 无实际持仓时，目标仓位提醒只能是框架复核，不能描述账户盈亏或精确调仓数量。
- 未校准的 record_only 信号可以要求研究复核，但不能直接升级成实时报警。
- 没有当前证据支持时，延期比勉强发消息更好。

## 消息结构

先写清楚“什么变了、为什么现在值得看”，然后给出规则与证据，再写候选复核动作、缺失输入和失效条件。不要在一条消息里重复多个不相关主题，不要把工具字段直接倒给用户。
