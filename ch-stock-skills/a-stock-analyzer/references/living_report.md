# 活报告结构契约（同一只股票的持续跟踪报告）

一份个股报告很少只写一次。第 2 次、第 N 次更新时如果没有结构约定，每轮都会临场发明放增量的地方，结果就是：更新章节把核心判断挤到页面深处、正文数字和更新章节互相矛盾、同一条历史被手写四遍、三情景表长出"初版 vs 重算"对照列。本文把"报告如何随时间生长"定成契约。**首版（v1.0）报告只需遵守 §1 骨架与 §4 核心判断尾块；其余条款从第一次更新开始生效。**

本契约的所有结构都是"渲染器认得出的写作惯例"：写对了，HTML 自动升级成时间轴、折叠卡、stat 网格、引用锚；写得不标准，也只是退回普通 Markdown，正文永远不受损（与 SKILL.md §2.3"内容与格式解耦、尽力而为"一致）。

---

## 1. 三层分工与文档骨架

更新历史只允许住在三层里，各管各的，不重复手写：

| 层 | 载体 | 职责 | 谁消费 |
|---|---|---|---|
| 正文 | 各章节 | **只有最新真相**（现行口径、现行结论） | 首次读者从头读 |
| 更新章节 | `## 更新 YYYY-MM-DD：一句话摘要` | 带日期的**增量叙事**（本轮发生了什么、为什么改/不改模型），append-only | 老读者只看新增 |
| 台账 | PG 跟踪表 + 文末「版本变更记录」表 | **机器可读的数字与版本轨迹** | 渲染器画时间轴、徽标、变更条 |

文档顺序固定为：

```markdown
# 标题
| 日期 | 版本号 | 两列表（渲染时被时间轴替换；纯 MD 阅读时保留可读）
## 核心判断（永远紧跟头部，含 §4 固定词表尾块）
## 更新 YYYY-MM-DD：…（新在前，逐次堆叠；HTML 折叠成卡片，默认只展开最新一节）
## 第一部分 · 定性 …
## 第二部分 · 定量 …
## 第三部分 · 背景与风险
## 后续跟踪清单（==跟踪事项== 卡片块，见 §7）
## 版本变更记录（四列台账，见 §8）
## 附：深度调研索引（Deep 模式，见 §9）
页脚免责
```

**更新章节永远放在核心判断之后、第一部分之前**。不要把更新节堆在核心判断前面——那会让新读者先啃增量 delta 才见到结论；折叠卡解决"老读者跳过正文"的问题，不需要靠物理置顶。

## 2. 更新章节契约

每节更新固定三块，标题格式必须是 `## 更新 YYYY-MM-DD：一句话摘要`（冒号后那半句就是折叠态显示的文案，写成"发生了什么+对结论的影响"，如"经营变量未变，激励登记落地，估值分母小幅回落"）：

1. **快照表（首块）**：`| 维度 | 最新值 | 相对上次 | 对模型的影响 |`。把本轮"变了什么、没变什么、影响什么"压进一张表；没变的关键维度也要列（写"不变"），读者才能确认"没变"是核实过而不是漏了。
2. **增量叙事（中间）**：新公告/新数据的事实与判断，照常写；涉及跟踪字段的数字挂 `{{track:字段id}}`。
3. **本轮结论（末块）**：一段话说清本轮改了什么、没改什么、为什么；随后列出本轮**状态发生变化**的跟踪事项（`TODO-xx：待跟踪 → 部分兑现，依据…`）与上/下修条件命中情况。

写完更新章节后必须同轮完成：① 变化字段 `tracking_table.py set` 落库；② §8 版本变更记录表加一行；③ §3 状态型小节刷新。这三件事就是"同一条历史只落一处、三层各自引用"的落地动作。

## 3. 正文的冻结与刷新分级

"正文=最新真相"不等于每轮全文重写。按小节性质分两类：

- **状态型（每轮更新必须刷新）**：公司速览、近期动态、估值结论六项、主线归属修正、同业对标表、核心判断。这些小节体量小、描述"现在"，留旧数字就是错误（例：速览还写 246 亿市值而更新章节已是 234.94 亿——这是本契约要杜绝的典型事故）。
- **论证型（允许冻结，但要带戳）**：行业地位与竞争格局、单机经济性推导、看点论证、成长成功率论据。冻结时在小节开头标 `（论证基准：YYYY-MM-DD，结论仍适用）`；一旦某轮更新推翻了论证本身，必须回来改正文，而不是只在更新章节里说。

**硬规则：会随时间漂移的关键数字（市值、收盘价、交付台数、远期净利、期望市值、隐含预期）必须在正文挂 `{{track:字段id}}`。** 这样即使某段 prose 冻结过期，读者点徽标就能看到最新值与完整轨迹，prose 与事实的偏差被机制兜底。禁止把"重算后的现行方法论"写进更新章节、正文留一句"见上方更新"——方法论的现行版本永远住在正文，更新章节只保留"从旧到新怎么变"的叙事。

## 4. 核心判断的固定词表尾块

核心判断 = 结论段（2-4 句，照旧）+ **固定词表 bullets 尾块**。词表（渲染器按这些标签抽 stat 网格）：

```markdown
- **公司类型**：转型期权股 / B 型成长
- **估值阶段**：预期定价、合理偏乐观
- **主线连接强度**：产业强连接｜短线退潮
- **成长成功率**：中性（偏谨慎）
- **当前市值**：234.94 亿元 {{track:current_mv}}
- **期望市值**：约 465 亿元 {{track:weighted_expected_mv}}
- **最关键变量**：租赁毛利上表；拿卡价
- **总体置信度**：中
```

每条**值 ≤ 20 字**（超长说明混进了论证，论证放正文）；市值/期望市值必挂跟踪点。渲染器识别 ≥2 条词表标签时把它们升格成 hero 卡底部的指标网格；标签外的 bullet 或超长值自动留在原处，不受影响。

## 5. "要观察什么"只登记一次：条件 ↔ 跟踪事项 ↔ 跟踪字段

同一个观察点（如"租赁毛利率 >40%"）天然会出现在三处：估值结论的上/下修条件、后续跟踪清单、PG 跟踪字段。规则是**跟踪清单为主档，其余两处只引用**：

- 每个跟踪事项有稳定 ID：`TODO-YYYYMMDD-简称-序号`（建档日期，不随更新改）。
- 上/下修条件逐条在行尾标注归属：`① 租赁毛利率连续两个报告期 >40% → TODO-01`。条件兑现与否的状态住在跟踪事项里，条件行不重复维护状态。
- 可量化的观察点同时建跟踪字段（§2.5），跟踪事项的「变量」行写字段 id，形成 条件 → TODO → 字段 的追溯链。
- 每轮更新在"本轮结论"里核销状态变化（§2 第 3 块），跟踪事项卡的状态徽标随之改（待跟踪 / 部分兑现 / 已兑现 / 证伪 / 更新观点）。

这一环打通后，报告就从"一篇文章"变成**可证伪的活清单**：读者在估值结论看到条件，点 TODO 查状态，点字段徽标看数字轨迹。

**首次建基线要 backfill 历史，别只落当日一条**。给一份已经更新过好几版的老报告补建 PG 跟踪表时，最容易犯的错是：每个字段只 `set` 一条当日值。这样 HTML 徽标浮层里每个字段只有一条记录、sparkline 画不出来（单点无走势），"看数字怎么变过来的"这个活报告的核心价值直接归零。正确做法是把正文与「版本变更记录」里**已经白纸黑字写着的历史数值**，按各自的历史日期逐条补进去：

```bash
# 同一字段按历史日期各补一条（--date 指定历史日，不带则默认今天）
tracking_table.py set 300209.SZ --field current_mv --value 246    --date 2026-06-02 --source 初版
tracking_table.py set 300209.SZ --field current_mv --value 236    --date 2026-07-07 --source 7-07收盘
tracking_table.py set 300209.SZ --field current_mv --value 241.45 --date 2026-07-08 --source 7-08节
tracking_table.py set 300209.SZ --field current_mv --value 234.94 --date 2026-07-13 --source 当前
```

- 数值字段（市值、期望市值、稳态净利、隐含台数）值只填数字、单位进 `--unit`，渲染器才能解析出 step 走势图；带单位或纯文字的值会退回"多条文本时间轴"（也对，只是没有走势线）。
- 只 backfill **正文已有据可查**的历史值，不为了凑点数编造中间值。缺某个历史日的值就跳过那条，不硬造。
- 之后每轮更新照常只对**变化字段**补当日一条（append-only，§三工作流第 5 步），历史自然越长越完整。

## 6. 三情景与估值的演化规则

- **三情景表永远只写现行口径**。禁止"初版 vs 重算"双列对照表——那是把版本轨迹塞进正文，更新两轮表就爆了。演化轨迹的归宿：推算变量挂 `{{track:}}`（steady_np、期望市值、合理倍数区间都该是跟踪字段），"为什么改"写在当轮更新章节，"改了多少"落在版本变更记录的关键数字列。
- 情景假设变更时正文表直接改成新值；旧值不留在表里，留在跟踪字段历史里。
- 估值结论六项照 SKILL.md §5.6 输出，其中"合理估值区间""当前估值"两项的数值挂跟踪点。

## 7. 跟踪事项卡片块（替代 10 列宽表）

后续跟踪清单不再用 10 列大表（HTML 里只能横向滚动），改为逐项卡片块：

```markdown
==跟踪事项｜TODO-20260602-行云-01｜业绩数据｜优先级：高｜状态：部分兑现｜更新：2026-07-08
事项：H1 预告确认算力收入已上表（以售机为主）；待验租赁租金上表与租赁毛利能否到 40%+。
变量：算力分部收入、租赁毛利率（leasing_economics）、合同负债
验证：H1/Q3 定期报告 + 巨潮公告原文
反证：租赁租金仍不上表 / 毛利 <15%
来源：[H1 业绩预告（公告 2026-095）](https://...)
==
```

首行竖线段依次为：ID｜类型｜优先级｜状态｜最近更新（状态词会被渲染成红黄绿徽标）。正文行只允许 `事项 / 变量 / 验证 / 反证 / 来源` 五个标签，其余行成为备注。已完结的事项不删除，状态改"已兑现/证伪"并保留——清单本身就是履历。

## 8. 版本表与版本变更记录

- 标题下保留两列极简表（`日期 | 版本号`，新在前）——纯 Markdown 阅读时的版本入口，HTML 渲染时被时间轴组件替换隐藏。
- 文末「版本变更记录」是版本台账，四列固定：`日期 | 版本 | 主要变更 | 关键数字变化`。每轮更新加一行；「关键数字变化」写口径跃迁（如"期望市值 224 → 465 亿"），这是时间轴节点弹层的内容来源。
- 版本号规则：首版 v1.0；接入新证据重估记 minor（v1.1）；只做跟踪/轻改记 patch 或沿用并注明；重写升 major。

## 9. 来源治理：索引是唯一台账

- Deep 模式的「深度调研索引」是**唯一**的来源台账。不再单独维护「信息来源」清单节——它与索引、frontmatter `primary_sources` 三处重复且各自漂移；frontmatter 需要时由索引生成。
- 正文引用来源用行内标号：`……售机毛利约 97 万/台 [W15]`。标号必须能在索引表第一/二列找到（W1、#12、对标 1 均可），渲染器会把 `[W15]` 变成跳到索引行的锚链 chip。发现卡（`==深度调研发现｜…`）照旧四行体，两者并存：发现卡承载"就近论证"，`[W]` 标号承载"轻量引用"。

## 10. 风险分层

风险提示分两组写：

- **特异性风险**（3-6 条，在前）：这家公司独有、能改变估值结论的风险，逐条给量化阈值或可观察信号，可挂 TODO。
- **例行风险**（一条指针，在后）：公告套话式的采购/履约/宏观/汇率类风险压缩成一条，指回公告原文（如"55 亿订单公告 §5 列示七类例行风险，见 [W14]"），不逐条抄进报告。

## 11. 更新一轮报告的自检清单

- [ ] 更新章节：标题带日期+一句话摘要？首块有快照表（含"不变"项）？末块有本轮结论+状态核销？
- [ ] 正文：状态型小节全部刷成最新（速览市值、对标表、估值结论、主线）？冻结的论证型小节有基准日戳、且没有被本轮推翻？
- [ ] 三层落账：变化字段已 `set` 落库？版本变更记录加了行？顶部两列表加了行？
- [ ] 一致性：正文任何地方不再出现旧市值/旧口径数字（有跟踪点的除外——徽标会给最新值）？三情景表是纯现行口径？
- [ ] 闭环：本轮涉及的上/下修条件在对应 TODO 里核销了状态？新观察点建了 TODO（和字段）？
- [ ] 首次建基线：把正文/版本变更记录里已有的历史数值按历史日期 backfill 了（§5），而不是每个字段只落当日一条？（否则浮层看不到演变、sparkline 画不出）
- [ ] 渲染：重跑 `render_report_html.py`，summary 里 `tracking_markers.stripped` 应为 0（有被剥除的说明正文挂了不存在的字段 id）；`tracking_updates` 明显大于字段数（说明历史有厚度，不是每字段单条）。
